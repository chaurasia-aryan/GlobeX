## 1. The disqualifying finding, restated precisely

The shipped labels are **rule-based heuristic labels**, generated by
`backend/brain/brain_prev/data_pipeline/scripts/build_canonical_parquet_v2.py:363-378`:

```python
z_score = (trade_value_usd - rolling_mean_3m) / rolling_std_3m
conditions = [ z_score > 3.0,
               unit_value_change_mom > 2.5,
               trade_growth_mom < -0.90 ]
anomaly_type = np.select(conditions, ['VOLUME_SURGE','PRICE_SPIKE','UNEXPECTED_COLLAPSE'],
                         default='NORMAL')
anomaly_flag = np.where(anomaly_type != 'NORMAL', 1, 0)
```

**All three quantities in that rule are also model input features:**

| Label-rule quantity | Model feature |
|---|---|
| `z_score` | `feature_list.json[13]` = `val_rolling_zscore` |
| `unit_value_change_mom` | `feature_list.json[6]` = `unit_value_change_mom` |
| `trade_growth_mom` | `feature_list.json[5]` = `trade_growth_mom` |

Re-applying that Boolean rule to the model's own feature columns reproduces `anomaly_flag` on
**12,288 of 12,288 rows — F1 = 1.0000, accuracy = 1.0000, zero false positives, zero false
negatives** (Phase 3 §5.1.4). `val_rolling_zscore` alone reaches **AUC 0.8566** against the label with
no model at all.

**Therefore `validation_f1 = 0.9818` is a rule-recovery score, not a detection score.** It measures
how well a gradient-boosted tree can re-derive a three-threshold Boolean function from the three
columns that function was computed on. It is not evidence of anomaly-detection skill and must never
be cited as such. Note also that the model **underperforms its own target**: the closed-form rule
gets F1 = 1.0000, the model gets 0.9818, so the classifier is a lossy compression of a rule anyone
can write in one line.

### 1.1 These labels are not fraud, and the repo already knew that

* `label_source` = `'RULE_BASED_HEURISTIC'` on **100.0%** of rows — the dataset labels itself.
* The repo's *other* labelling script, `build_anomaly_labels.py` (not the one that produced the
  shipped data), states in its own docstring at lines 36-37: *"These are statistical discrepancy
  flags, NOT criminal fraud ground truth."*
* There is **no investigated-case outcome, no customs finding, no adjudication, and no confirmed
  fraud record anywhere in this repository.** Nothing in this system has ever been validated against
  a real fraud determination.

Per `18_TRADE_ANOMALY_PRODUCTION.md` the required separation is absolute:
`Anomaly ≠ Fraud ≠ Sanctions ≠ Legal violation`.

### 1.2 The rule structurally cannot detect under-invoicing

Phase 3 §1.7, measured at runtime on an adversarial input with unit value $0.02/kg, a −95% MoM price
move and z = −4.5:

```
benign_baseline     score = 0.000241   flagged = False
extreme_undervalue  score = 0.000403   flagged = False   <-- under-invoicing, NOT flagged
extreme_spike       score = 0.999520   flagged = True
new_corridor        score = 0.000236   flagged = False
all_zero_numeric    score = 0.000202   flagged = False
```

This is not a tuning failure, it is a definitional one. The label fires only on **upward** z-score
spikes (`z > 3.0`), **upward** unit-value moves (`> 2.5`) and **value collapses** (`< −0.90`). A
*downward* price deviation at constant volume — the canonical trade-mis-invoicing pattern, and the
one customs authorities care most about — is `NORMAL` by construction. Any model trained on these
labels inherits that blind spot exactly.

Also measured: `unit_value_change_mom > 2.5` fires on **0 of 12,288 rows**, so the `PRICE_SPIKE`
class never appears in the data at all. **The system advertises three anomaly types and has training
evidence for two.**

### 1.3 Categorical features contribute nothing

Phase 3 §1.4, measured:

```
hs6=090111 iso=ARE : score = 0.000241   onehot_nonzero = 1/3
hs6=999999 iso=ZZZ : score = 0.000241   onehot_nonzero = 0/3
hs6=847130 iso=USA : score = 0.000241   onehot_nonzero = 2/3
```

Identical to six decimal places across in-vocabulary, partly-in-vocabulary and entirely
out-of-vocabulary inputs. The `OneHotEncoder` uses `handle_unknown="ignore"`, so any HS6 outside the
trained 8 codes or any country outside the trained 16 is silently encoded as an all-zero block and
scored anyway, with no error and no coverage warning at the model layer. **The model is driven
entirely by its 17 numeric features; the product and country inputs are decorative.**

The service layer partly mitigates this — `inference.py:154` rejects corridors with fewer than 3
historical observations as `INSUFFICIENT_HISTORICAL_CONTEXT` — which indirectly blocks most
out-of-vocabulary requests. That guard is correct and should be kept.

### 1.4 The calibrated threshold is never used

`src/trade_anomaly/inference.py:217`:

```python
threshold = float(self.threshold_config.get("anomaly_threshold", 0.50))
```

`threshold_config.json` contains the keys `['optimal_threshold', 'f1_score']`. **`anomaly_threshold`
does not exist**, so the lookup never matches and the hardcoded `0.50` always wins, silently
discarding the calibrated `0.45`. `XGBoostAnomalyModel.predict()` (`models.py:111`) defaults to `0.5`
as well — two independent paths bypass the calibrated value. Separately, the 0.45 itself has **no
documented calibration method**: no sweep code, no PR curve, no per-threshold table, no calibration
plot, and no probability calibration (no Platt, no isotonic), while `scale_pos_weight=9.0` during
training actively distorts raw probabilities away from being likelihoods.

**The output field named `anomaly_score` is not a probability** and must not be presented as one.

## 2. Why no alternative models were trained in this phase

The pack's Phase 5 text asks for multiple model families to be evaluated where feasible — Isolation
Forest, MLP/GRU autoencoder, TCN, Transformer. **That is not feasible against these labels, and
attempting it would produce a misleading result.**

The target is a closed-form Boolean function of three inputs that are themselves supplied to the
model. Any supervised learner given those three columns will approach F1 → 1.0, because the mapping
is exact and noiseless. A comparison table showing "Isolation Forest 0.94, TCN 0.98, Transformer
0.99" would measure nothing except each architecture's capacity to represent two threshold cuts, and
publishing it would manufacture false confidence in a detection capability that does not exist. The
same objection applies to PR-AUC and F1 against these labels: **every such metric is contaminated at
the source, so no amount of temporal validation rescues it.** Phase 3 §5.1.5 already confirmed the
chronological split is correct — and it does not help, because the leak is definitional, not
temporal.

Unsupervised alternatives (Isolation Forest, autoencoder reconstruction error) would avoid the label
leak but have no trustworthy evaluation target to be scored against, since the only labels available
are the leaked ones. Building them properly is a real ML engineering project requiring new label
design first — out of scope here, and recorded as backlog in §3.

**Doing nothing new and saying so plainly is the correct engineering answer at this point.** The
model is not underfit or mis-tuned; the supervision signal is invalid.

## 3. Backlog — what a valid remediation would require

Documented, **not implemented**. Ordered by dependency: item 1 gates everything after it.

1. **Design a label that is independent of the model's inputs.** Mandatory precondition. Either:
   * **(a) Real investigated outcomes.** The strongest option. Requires a source that does not
     currently exist anywhere in this repo — customs adjudications, post-clearance audit findings,
     confirmed mis-declaration cases, or platform dispute resolutions with a verified determination.
     Until such a source exists, no supervised anomaly model in this system can make a detection
     claim of any kind.
   * **(b) A different heuristic basis, with strict feature/label separation.** If real outcomes are
     unavailable, a heuristic label is acceptable *only* if the columns used to build it are
     **excluded** from the feature set, and the separation is enforced by a test in CI. Candidate
     bases that are not currently model inputs: mirror-trade reconciliation (exporter-declared vs
     importer-declared value for the same flow), cross-corridor peer deviation (this corridor's unit
     value vs the same HS6 to comparable destinations in the same month), and declared-weight vs
     declared-quantity inconsistency. All three are genuinely independent signals. **Mirror-trade is
     the obvious first candidate and is currently impossible**: `mirror_ratio` (constant 1.0),
     `mirror_difference` (100% zero) and `mirror_missing_flag` (100% zero) are hardcoded placeholders
     assigned at `build_canonical_parquet_v2.py:359-362`. The columns exist; the reconciliation does
     not. Building it is a data-pipeline task, not a modelling task.

2. **Add under-invoicing coverage explicitly.** The current rule structurally cannot catch it (§1.2).
   Any replacement label set must include a **downward** unit-value deviation condition —
   symmetric to the existing upward one — and the resulting model must be regression-tested against
   the `extreme_undervalue` case from Phase 3 §1.7, which must flag.

3. **Retain the causal rolling-feature construction.** This is the one thing about the pipeline that
   is unambiguously correct (Phase 3 §6): the lagged `[t−3, t−1]` rolling window contains no future
   information. The defect is definitional leakage, not temporal leakage. **Do not "fix" the feature
   pipeline — it is not broken.**

4. **Clean the corridor vocabulary before retraining.** `partner_iso3` includes `'IND'` (India as its
   own trade partner) and `'WLD'` (the World aggregate), both in the model's trained vocabulary. The
   `WLD` rows double-count every bilateral flow; the `IND` rows are self-trade. Neither is a real
   corridor.

5. **Drop one of `quantity` / `net_weight_kg`.** They are equal on 12,288 of 12,288 rows (100.0%) yet
   both are model features. The baseline EDA notebook observed this in cell 38 and it was not acted
   on.

6. **Reconcile the `partner_share_pct` scale.** It is a 0-1 fraction in the anomaly dataset and a
   0-100 percentage in the partner-discovery dataset, under the identical `_pct` suffix. Worse,
   `build_canonical_parquet_v2.py:352` multiplies by 100 while the live-inference recomputation in
   `feature_pipeline.py:135-139` does not — **the training column and the serving column differ by
   100×.** This is a live train/serve skew and should be fixed regardless of what happens to the
   model.

7. **Widen coverage, or enforce it.** The model has seen 8 HS6 codes and 16 countries. Either
   retrain on the full product/country space, or make the coverage limit an explicit, returned field
   so callers can see when they are outside it (see §5).

8. **Calibrate and persist a threshold properly.** Sweep on the validation split, save the PR curve
   and the per-threshold table alongside the artifact, apply isotonic or Platt calibration so the
   output is a probability if it is going to be named like one, and read the key the file actually
   contains.

thing here, and it is not a model.

## 5. PRODUCTION DECISION

**Retire, replace with: the transparent three-threshold statistical screen the model already
reproduces exactly, relabelled as a screen and not as detection.**

The classifier adds nothing over a rule that can be written in one line and evaluated in
microseconds, and it reproduces that rule *less* accurately (F1 0.9818 vs the rule's 1.0000). Keeping
a 254 KB gradient-boosted model, a custom pickled preprocessor, a `sys.path` dependency on the source
tree, and a broken threshold lookup — in order to approximate three comparisons — is pure operational
cost for negative benefit. Replace it with the rule, state the rule publicly, and stop implying a
learned detection capability that no evidence in this repository supports.

Concretely:

* **Serve** `flag = (val_rolling_zscore > 3.0) or (unit_value_change_mom > 2.5) or
  (trade_growth_mom < −0.90)`, computed from the existing causal feature pipeline, which is correct
  and should be kept.
* **Return the driver**, not a score: which condition fired and by how much. That is genuinely more
  actionable than `0.000241` and is honest about what the system did.
* **Keep** the `< 3 observations → INSUFFICIENT_HISTORICAL_CONTEXT` guard at `inference.py:154`. Per
  the pack's cold-start rule, do not manufacture a normal baseline for a corridor with no history.
* **Add** a returned `coverage` block stating whether the requested HS6 and country are inside the
  8-code / 16-country envelope, so out-of-envelope requests are visibly out of envelope rather than
  silently scored.
* **Fix the `partner_share_pct` 100× train/serve skew** (§3 item 6) regardless — it affects the
  feature pipeline, which survives this decision.
* **Keep** `xgboost_anomaly_model.joblib` on disk as a research artifact with a README pointing at
  this report. Do not load it; do not cite `validation_f1 = 0.9818` anywhere, in any deck, README,
  API response, or UI string.
* **Do not** retrain any architecture against the current labels (§2).

```json

  "method_label": "Statistical screen — unusual trade pattern vs this corridor's own 3-month history",
```

Mandatory UI and copy rules, per `18_TRADE_ANOMALY_PRODUCTION.md` and
`12_UI_COMPLIANCE_REQUIREMENTS.md`:

* The user-facing string must be of the form **"Unusual trade pattern detected — statistical screen,
  not a fraud finding."** The words *fraud*, *illegal*, *money laundering*, *tax evasion*,
  *smuggling*, *sanctions violation* and *criminal* must not appear anywhere in this feature's copy,
  in any severity level, including `CRITICAL`.
* The screen result must be rendered in its **own panel**, visually and structurally separate from
  destination ranking, sanctions status and compliance status. It must never be summed, averaged or
  blended into a single composite "risk" number with them.
* `known_blind_spots` must be shown, not hidden. A user must be able to see that a clean screen does
  **not** mean the trade is clean — under-invoicing is invisible to this screen by construction.
* The current frontend displays `Score {anomaly_score * 100}/100`
  (`src/pages/TradeAnalysisPage.tsx:242-243`) with no provenance label, and falls back to a
  hardcoded `anomaly_score: 0.18, anomaly_type: "NORMAL"` when the API is unreachable
  (`src/services/api/aiService.ts:587-590`). Both must change: the score display must be replaced by
  the driver text, and the hardcoded fallback must render the pack's
  **`DEMO DATA — NOT LIVE COMPLIANCE`** banner rather than a plausible-looking clean result.
* A flag may set the pack's `REVIEW REQUIRED` state. **It may never set `BLOCKED`.** `BLOCKED` is
  reserved for a verified applicable legal prohibition, which this screen does not and cannot
  establish.
